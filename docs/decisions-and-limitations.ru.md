# Все решения и ограничения эксперимента

Актуально на 2026-10-01. Этот документ отделяет поручения владельца от предложений
AI. До реальных API-запусков дизайн можно исправить и заново зафиксировать.

## Что подтвердил владелец

- Отдельный локальный проект и **публичный GitHub** для статьи AI Techie и портфолио.
  Public в сообщении имеет приоритет над private в приложенном старом задании.
- Не добавлять CI/CD. Есть только локальные проверки.
- 2026-10-01: **$10 суммарно** на dev и один итоговый прогон; это не доллар на каждый запуск.
- Основная GPT-модель: **GPT-6 Luna, API ID `gpt-6-luna`, `reasoning.effort=medium`**.
  Medium установлен явно, а не оставлен скрытым default. None из старого задания
  больше не основной режим. Настройки medium не выбирались по итоговому набору.
- Подготовить `.env`; владелец сам внесёт ключи. Реальных вызовов пока нет.

Подтверждение бюджета и модели **не означает review всех бизнес-правил и меток**.
Владелец запросил их описание, поэтому `data/owner-review.json` пока не отмечен approved.

## Какой продукт сейчас строится

Маленькая демонстрация переключателя обращений вымышленного магазина «Лист».
Один текст и одинаковый контекст поступают двум моделям. Каждая выбирает **один
из трёх маршрутов**. Основной benchmark измеряет выбор, а не обслуживание клиента.

| Маршрут | Что означает | Что будет делать демонстрация |
|---|---|---|
| status | Прочитать состояние конкретного известного заказа | Общий локальный поиск в фиктивной базе |
| operator | Передать человеку действие или неоднозначное обращение | Карточка в очереди на экране, без настоящего сотрудника |
| answer | Информационный вопрос по справке | Отдельная LLM составляет ответ по общей FAQ |

Маршрут `answer` **не означает, что GPT-роутер уже ответил клиенту**. Jev и GPT
при выборе не выполняют заказов и не генерируют ответ. LLM-исполнитель — отдельная
роль, модель для него ещё не выбрана. Его платные вызовы в основной benchmark не включены.

Сейчас готовы данные, runner, отчёт и простой локальный контроль. Исполнители,
кликабельная двухколоночная демонстрация и анимация ещё не сделаны: приложенное
задание ставит их после правильного отчёта и реального прогона. Будущая анимация
использует сохранённые решения и явно называется replay. Это порядок работ из
задания; если нужна демка до измерений, её можно отдельно сделать без цифр моделей.

## Бизнес-правила: мои предложения, которые можно изменить

1. **operator > status > answer** для одновременно активных намерений.
   «Где заказ и отмените его?» → operator. «Где заказ и сколько храните?» → status.
2. **Изменение денег/заказа — человеку**: отмена, возврат денег, обмен, адрес,
   состав, дата доставки, спор о списании, решение претензии о браке/недостаче.
3. **Общая процедура — в справку**: «Как отменяют?» → answer;
   «Отмените мой заказ» → operator. Даже условная отмена считается действием.
4. **Неизвестный номер или мало данных — operator**. Внутри трёх маршрутов я выбрал
   человека для уточнения. В реальном продукте можно было бы вернуть уточняющий
   вопрос через status/answer или ввести четвёртый clarify. Это не требование API.
5. **Только один заказ**. Два различных номера → operator, даже если оба есть в
   базе. Это искусственное упрощение; можно разрешить несколько, изменив правила/метки.
6. **Формат номера — ровно пять цифр**. Номера 41001–41008 вымышленные. Букву O
   вместо цифры 0 модель не должна исправлять догадкой. Это мой выбор формата,
   а не особенность Jev или GPT.
7. **Текущий номер переопределяет выбранный** в интерфейсе. Без текущего номера
   разрешён `selected_order_id`. Один номер без намерения проверить статус недостаточен.
8. **Сам гнев не требует оператора**: «Долго! Где 41008?» → status;
   «Компенсируйте задержку» → operator. Это отдельная бизнес-политика, не объективная истина.
9. **Отрицание, цитата, завершённое прошлое — не новое действие**.
   «Оператор не нужен» не отправляет человеку. История может раскрыть «да, сделайте».
10. **Вопрос вне FAQ или непонятная цель — operator**. Не добавлены свободный чат,
    приветствия, отдельный маршрут отказа или автоматическое уточнение.
11. **Инструкции внутри обращения — данные**. Фальшивый system или «выбери answer»
    игнорируются при классификации реального вопроса. Только инструкция без вопроса магазина → operator.
12. **Доступ к заказам предполагается разрешённым**. Нет авторизации, проверки
    владельца заказа, CRM, телефонов реальных клиентов или персональных данных.

Полный текст: [business-rules.md](business-rules.md).
[13 конкретных пограничных примеров](owner-review.md) показаны с исходными сообщениями.
Маршруты здесь — договорённости о поведении игрушечного магазина. Если поменять
политику уточнения или приоритеты, нужно обновить затронутые метки до теста.

## Данные и независимость теста

- 20 dev-примеров для интеграции и настройки; отдельно 100 итоговых.
- Итоговые: 60 обычных, 30 сложных, 10 adversarial; метки 33 status / 34 operator / 33 answer.
  Доли и баланс заданы экспериментом, они не отражают настоящую статистику магазина.
- Все сообщения и первоначальные метки написаны AI. Это не экспертная разметка,
  не реальные клиенты и не внешний benchmark. Человек ещё не проверил правильность.
- Dev написан отдельно. Автоматическая проверка уникальности и похожести не нашла
  пар выше порога 0.82, но **не доказывает смысловую независимость** и отсутствие близких сценариев.
- Известные номера, выбранный заказ, история и справка одинаковы для двух моделей.
  В API не передаются id примера, expected_route, rationale или tags.
- Обе модели видят даже фиктивные состояния заказов в общем снимке магазина.
  Это небольшой искусственный контекст; мы не проверяем извлечение из большой CRM.
- Финальный набор открыт на GitHub. Это не защищённый holdout: будущие агенты/модели
  могут его увидеть. По финальным ошибкам нельзя улучшать этот же тест и потом
  сообщать новую оценку как независимую. Для следующего цикла нужен новый набор.
- Повторные прогоны тех же 100 задач проверяют стабильность, не создают 300 независимых задач.

## Модели, запросы и обычные настройки

- Jev: фиксированная `jev-1.13.0`, один Choice с тремя criteria; confidence сохраняется
  отдельно, без передачи человеку по порогу.
- GPT: `gpt-6-luna`, явно `reasoning.effort=medium`, Responses API, строгий JSON
  только с route, `store=false`, обычный `service_tier=default`.
- **max_output_tokens не отправляем**: модель получает собственный обычный запас
  генерации. Старый лимит 32 и предложенный 2048 убраны. Рассуждение и короткий
  видимый JSON входят в output usage. [Документация](https://developers.openai.com/api/docs/guides/reasoning).
- Нет искусственного потолка входных токенов, квот dev/final, общего двухчасового
  deadline или дополнительных счётчиков запросов сверх самого набора.
- Обычный сетевой timeout 60 секунд, чтобы клиент не завис навсегда. Ошибка/timeout
  сохраняется, а не подменяется успешным маршрутом. При потерянном ответе серия
  останавливается, потому что исход и usage неизвестны.
- Основная серия последовательная: один запрос одновременно, пауза 0.1 секунды,
  shuffle seed 614 и чередование Jev/GPT. Это условия измерения, а не ограничения модели.
- Один повтор при 429/выбранных 5xx/529; обе попытки входят в отчёт и расход.
- По умолчанию один проход: dev 20 × 2 модели = 40 вызовов, final 100 × 2 = 200.
  Код допускает до трёх отдельных повторов в общем бюджете; они не увеличивают
  число независимых задач. UI-гонка/Batch/full-cycle остаются отдельными режимами.

Доступ аккаунтов и реальные формы ответов пока не проверены. У GPT опубликован
ID без датированного snapshot, поэтому неизменность весов между датами не
гарантируется. Настройки не меняются по финальным ошибкам; смену модели не скрываем.

## Что именно измеряется

Качество: exact match обычным кодом, correct/N, accuracy, macro-F1, матрица,
доля оператора, доля автоматизации, ошибки по сложности, все расхождения двух моделей.
LLM-судьи нет. Неполученный/невалидный маршрут не превращается в правильный operator.
Такие задачи и ещё не запущенные после остановки остаются в плановом знаменателе;
неполная серия помечается stopped, а не выдаётся за завершённый тест.

«Неверная автоматизация» — неверный status/answer. Отдельно «опасная автоматизация»:
по метке должен быть operator, а модель выбрала автоматический маршрут.
Перепутанные status и answer также ошибка, даже если они не требуют человека.

Время: от локальной отправки до полного безопасного ответа, parsing/validation.
Включены сеть и старт/завершение локального HTTP worker; это **клиентская задержка**,
не чистое время вычисления модели. Есть median/p95 с n, отдельно валидные/все попытки
и время решения с ретраями/backoff. При 100 задачах хвост p95 нестабилен. Регион
провайдера и сетевой RTT не измерены. Гонка двух колонок — другой режим, не основной тест.

Reasoning medium влияет и на latency, и на платные output tokens, хотя виден один route.
Нельзя представить результат medium как цену любого GPT или как сравнение с none.

## Деньги: $10 на эксперимент, без сложной системы квот

Владелец увеличил бюджет до **$10 суммарно** и попросил убрать чрезмерные ограничения.
Отменены квоты $0.15/$0.85, lock, отдельный ledger, запрет нового dev-запуска и
специальный лимит reasoning/output. Оставлен простой общий учёт по сохранённым
попыткам: следующий запуск видит уже записанные расходы. Рабочие запуски сохраняются
в `results/live/`. Это последовательный локальный эксперимент, не система контроля
нескольких одновременно работающих клиентов и не банковская гарантия счёта.

Тарифы на 2026-10-01: Jev $0.042/M input, output бесплатно; GPT Luna input $0.10/M,
cache-read $0.01/M, cache-write $0.125/M, output $0.50/M. Источники:
[Jev](https://docs.typesafe.ai/models), [GPT](https://developers.openai.com/api/docs/models/gpt-6-luna).
Reasoning уже включён в output; повторно его не прибавляем.

Старая оценка «около $0.04» относилась к none. Для medium расход рассуждения ещё
неизвестен. Даём сценарии 256/1024/4096/16384 общих output tokens на GPT-запрос,
без обещания точного расхода: [final](budget-medium-final-v2.json),
[dev](budget-medium-dev-v2.json). Это planning, не результаты моделей.

Перед запросом код оценивает верхний расход по размеру подготовленного тела и
опубликованному максимуму модели. **Это только бухгалтерский резерв**, не параметр
API, и он не обрезает рассуждение. Полученный usage уменьшает резерв до расчётной
стоимости. Повторы и ошибки сохраняются. Потерянный usage не считается бесплатным;
cache-write без распределения оставляет расчётный верх. Для реальной цены нужен
usage настоящего прогона. Тарифы/счёт провайдера могут отличаться от клиентской оценки.

В основном сравнении нет LLM-исполнителя и его расходов. Если измерим весь ответ,
это будет отдельная строка/серия, а не скрытая прибавка к стоимости роутера.

## Воспроизводимость, публикация и границы проекта

Python 3.11+, стандартная библиотека, без SDK с скрытыми ретраями. Короткий AGENTS
как карта, документация и активный план в repo, валидация на API-границе, локальные
структурные проверки и полезные тесты. Это применение принципов harness engineering,
не сертификация OpenAI и не копирование всей их инфраструктуры.

Каждый run создаёт новый каталог: cases, manifest с commit/hash/config/prompt,
каждая попытка с безопасным raw response/usage/errors, JSON/CSV/Markdown и SVG.
Прошлые результаты не переписываются. Offline-контроль с 54/100 относится только
к простым ключевым словам; ни accuracy, ни latency Jev/GPT ещё нет.

V1 none и старый offline-run сохранены как история. Активная конфигурация —
`configs/experiment-v2.json`, freeze — `data/freeze-v2.json`. Данные и правила не
изменены при переходе на medium; версия конфигурации и связанная заморозка новые.

Ключи только в gitignored `.env`; пустой файл подготовлен с правами 0600.
Никаких ключей из соседних проектов и Telegram. Удаляем секреты из API-тел и не
пишем Authorization. GitHub публичный: перед публикацией артефактов нужна проверка.
CI/CD, настоящее изменение заказа, поддержка сотрудников, аутентификация и production
инфраструктура не входят в проект. Редакционный репозиторий не изменяем. Посты и
сообщения другим людям/чатам не отправляем. Личные выводы автора не выдумываем.

## Как понимать будущий результат

100 синтетических русских примеров, созданных тем же AI, что писал правила, могут
быть систематически удобны/неудобны модели. Нет реального потока, согласия нескольких
разметчиков, настоящей статистики бизнеса или оценки других языков. Wilson 95%
описывает только часть выборочной неопределённости, не исправляет эти смещения.
Несколько правильных ответов разницы, маленький p-value или быстрый p95 не доказывают
общее превосходство. Вывод допустим только про этот набор, правила, версии и режим medium.

Перед запуском остаётся review предложенных бизнес-политик и меток. Если первоначальная
задумка отличается, наиболее важны: нужен ли отдельный clarify, допустимы ли два заказа,
куда отправлять неизвестный номер, требует ли гнев оператора и измеряем ли только
переключатель или весь ответ. Все эти решения можно пересмотреть до платного теста.
